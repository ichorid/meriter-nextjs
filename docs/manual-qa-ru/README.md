# Ручное тестирование Meriter (dev.meriter.pro)

Полный план проверки платформы **через интерфейс** перед выкладкой на production.

**Окружение:** https://dev.meriter.pro  
**Вход:** обычная аутентификация (email magic link и т.п.) — **не** fake-кнопки на login.

На удалённом dev **нет** режима fake user / fake superadmin и **нет** dev-инструментов (Seed demo world, «Создать тестовое сообщество» и т.д.). Команда выдаёт тестировщику **superadmin** на его рабочий аккаунт; дальше используются **уже существующие** данные на dev или создание сущностей через обычный UI.

---

## После полного прогона (триаж)

Остатки, не вошедшие в ship-day (P2, UX-бэклог, отклонённые идеи): [BACKLOG-AFTER-FULL-QA.md](./BACKLOG-AFTER-FULL-QA.md).

## Как пользоваться

1. Получить от команды: доступ на dev + роль **superadmin** на ваш аккаунт (+ второй аккаунт для двух пользователей, если нужно).
2. Прочитать [00-podgotovka-i-okruzhenie.md](./00-podgotovka-i-okruzhenie.md).
3. Выполнять сессии **по порядку** (00 → 14).
4. В каждой сессии заполнять колонку **«Фактически»** и таблицу багов в конце файла.
5. Production (сессия 14) — **только после** обязательных сессий на dev.

## Критерий «можно на production»

- [ ] Сессии **01, 02, 04, 05, 11, 12** — без блокирующих дефектов.
- [ ] Сессии **03, 06, 07** — пройдены или «не применимо» с пояснением.
- [ ] Вход по **email** на dev и prod работает (сессии 01 и 13).
- [ ] Сессия **14** — без критичных ошибок.
- [ ] Блокеры заведены в трекер и согласованы с командой.

## Что не входит в этот план

- Автотесты (`pnpm test`) — запускает разработчик.
- Telegram-вход — **отключён**; отсутствие виджета — норма.
- Fake-кнопки и dev-only seed на **удалённом dev** — **не ожидаются**; их отсутствие не баг.
- `wallets.withdraw` / `wallets.transfer` в API — не реализованы; не считать багом UI.

## Два участника на dev

1. Основной аккаунт (superadmin) — создание контента, настройки.
2. **Второй аккаунт** — отдельный login (второй браузер / инкогнито) или приглашение в сообщество по ссылке.

Уточните у команды второй тестовый login, если нужны сценарии «два пользователя».

## Локальный dev (опционально)

Если когда-либо тестируете **localhost** с включённым fakeDataMode — там могут быть Fake user и dev-инструменты. Этот план ориентирован на **dev.meriter.pro**; локальные отличия не обязательны к прогону.
