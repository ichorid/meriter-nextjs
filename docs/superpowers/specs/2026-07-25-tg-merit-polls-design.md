# Голосования заслугами для Telegram MVP — дизайн

Дата: 2026-07-25
Статус: согласовано с продуктом (вариант A)

## Проблема

Пользователи Telegram MVP собирают заслуги с меритер-ботом, но тратить их в
контексте чата почти некуда. Нативные опросы Telegram не подходят: один голос
на человека, без веса, без «против». Нужно голосование, где вес голоса —
потраченные заслуги.

## Требования (продукт)

1. Участник голосует, начисляя выбранному варианту выбранное количество заслуг
   со своего счёта (кошелёк). Квота по умолчанию **не участвует**; может
   включаться настройкой конкретного голосования.
2. Голосовать можно «за» и «против» варианта.
3. Голосовать в одном опросе можно несколько раз (суммы накапливаются).
4. Виден список «кто как проголосовал и сколько заслуг отдал» — всем
   участникам сообщества.
5. Основной UX — вкладка «Голосования» в миниаппе (`community-web`);
   бот в чате даёт только анонс, список идущих голосований и итоги + ссылку.
6. Кто может создавать голосования — настройка сообщества (лиды или все
   участники).

## Решение (обзор)

Расширяем существующую сущность **Poll** (`polls` + `poll_casts`) — она уже
даёт merit-взвешенное многократное голосование с записью кто/сколько/из какого
источника. Добавляем направление голоса, режим «только кошелёк», публичную
ленту голосов, выводим опросы в tRPC-роутер миниаппа, строим вкладку в
`community-web` и анонсы в боте.

Из скоупа исключено: кнопки голосования в чате (callback-панели), изменение
механики квоты в остальной платформе, отзыв/редактирование уже отданных
голосов.

## 1. Модель данных

### PollCast (`poll_casts`, `PollCastSchema` в shared-types)

- Новое поле `direction: 'up' | 'down'`, default `'up'` (легаси-записи без
  поля считаются `'up'`).
- `amountQuota + amountWallet > 0` — без изменений.
- Для `direction: 'down'` допускается только `amountWallet` (квота = 0).

### PollOption (`PollOptionSchema`)

- Новые поля `amountUp: number`, `amountDown: number` (default 0).
- `amount` = итог (`amountUp − amountDown`), может быть отрицательным — как
  рейтинг поста. Для легаси-опросов `amountUp` инициализируется из `amount`
  лениво (при первом касте) или миграционно не трогается: читатели считают
  `amountUp ?? amount`, `amountDown ?? 0`.

### Poll (`PollSchema`)

- Новый блок `settings: { quotaAllowed: boolean }`, default
  `{ quotaAllowed: false }`.
- Отсутствие блока (легаси) читается как `quotaAllowed: false`. Это осознанное
  изменение поведения старых опросов в вебе: квота по умолчанию больше не
  тратится.

### Community settings

- Новое поле `settings.pollCreation: 'admin' | 'members'`, default `'members'`
  (по образцу `eventCreation`). Проверяется в `CreatePollUseCase`.

## 2. Merit-механика каста

| Направление | Источник | Эффект |
|---|---|---|
| `up` | Кошелёк; квота участвует только если `poll.settings.quotaAllowed` (тогда приоритет квота → кошелёк, как сейчас) | Сумма добавляется к `amountUp` варианта |
| `down` | Только кошелёк (квота запрещена всегда) | Сумма добавляется к `amountDown`; заслуги голосующего сгорают (burn), как downvote поста |

- Кошелёк списания резолвится как сейчас (`MeritResolverService`, operationType
  `voting`): глобальный для приоритетных хабов/`isProject`, иначе локальный
  кошелёк сообщества — для TG MVP сообществ это локальный кошелёк, где и
  копятся заслуги от бота.
- Валидация: `expiresAt` в будущем, `isActive`, баланс достаточен; отрицательный
  баланс невозможен.
- Многократные касты одного пользователя (в т.ч. в разные варианты и в разных
  направлениях) — без ограничений, всё уже так работает.
- `referenceType` дебета кошелька остаётся `poll_cast`.

## 3. API (tRPC)

### Основной роутер `polls.*` (веб)

- `polls.cast`: вход дополняется `direction?: 'up' | 'down'` (default `'up'`).
  Сервер применяет правила источника из §2 (клиентский сплит квота/кошелёк
  игнорируется, как сейчас).
- `polls.getResults`: в ответ добавляется разбивка `amountUp` / `amountDown` /
  `amount` (итог) по вариантам.
- Новый `polls.getCasts({ pollId, optionId?, skip, limit })`: пагинированная
  лента кастов, обогащённая `userDisplayName` / `avatarUrl`; поля: пользователь,
  вариант, сумма, направление, время. Доступ — участникам сообщества опроса
  (существующий membership-чек). Дополнительно `polls.getCastersSummary`
  (или поле в том же ответе): агрегат по участникам (сумма за/против) для
  «топа голосующих».
- `polls.create`: вход дополняется `settings.quotaAllowed?`; добавляется
  проверка `pollCreation` (admin → лид/суперадмин).

### Роутер миниаппа `community-app.router` (`/trpc/community`)

Сейчас опросов там нет. Добавляются процедуры-делегаты к тем же use-case'ам:
`polls.listByCommunity`, `polls.getById`, `polls.create`, `polls.cast`,
`polls.getCasts` (+ данные баланса уже доступны существующими процедурами).

## 4. Миниапп (`community-web`) — вкладка «Голосования»

- Роуты: `/c/{communityId}/polls` (список), `/c/{communityId}/polls/[pollId]`
  (карточка), `/c/{communityId}/polls/create` (создание, виден по
  `pollCreation`). Пункт «Голосования» в навигации сообщества.
- Список: активные (таймер до `expiresAt`), ниже завершённые с итогами.
- Карточка голосования:
  - варианты с прогресс-барами: за / против / итог;
  - выбор суммы: пресеты 1/3/5/10 + произвольная;
  - кнопки «За» / «Против»; баланс пользователя рядом; сколько я уже вложил
    в каждый вариант (`getMyCasts`);
  - блок «Кто голосовал»: лента кастов + топ участников.
- Стиль — Obsidian Nocturne, копия «Заслуги» (см. design-system).
- Deep link: `startapp=poll:{pollId}` — расширить `tg-boot-resolve.ts`
  (паттерн `post:{id}` уже есть) → редирект на карточку голосования.

## 5. Бот (анонс + ссылка, без кнопок голосования)

- **Анонс при создании**: если у сообщества есть `telegramChatId` (и бот не
  заморожен) — сообщение в чат: вопрос, варианты, дедлайн + inline url-кнопка
  «Открыть голосование» → `https://t.me/{bot}?startapp=poll:{pollId}`.
  Реализация — по образцу `mirror-publication-to-telegram.use-case.ts`
  (событие/хук после `CreatePollUseCase`).
- **Команда `/polls`** в группе: список активных голосований сообщества со
  ссылками (routing как у `/balance` — ephemeral/DM по настройке).
- **Итоги по дедлайну**: cron (по образцу post-closing cron) находит опросы с
  истёкшим `expiresAt`, ещё не отмеченные как «итоги отправлены», ставит
  `isActive: false` (если ещё активен), шлёт в чат итоговое сообщение
  (победивший вариант, суммы за/против, число участников) и помечает опрос
  (`resultsAnnouncedAt`).

## 6. Тесты

- e2e (api): cast с `direction: 'down'` — wallet-only, burn, `amountDown`;
  quota отклоняется при `quotaAllowed: false` и принимается при `true`
  (только для `up`); многократные касты; `getCasts` — membership-гейт и
  корректная лента; `pollCreation: 'admin'` запрещает участнику.
- Unit: пересчёт `amountUp/amountDown/amount`; легаси-чтение (без полей).
- Bot: unit на построение анонса/итогов (формат сообщения, deep link).

## 7. Этапы реализации

1. **Бэкенд**: shared-types, схемы, cast use-case (direction/источники),
   `getCasts`, `getResults` разбивка, `pollCreation`, community-app router,
   тесты.
2. **Миниапп**: вкладка, список, карточка, лента голосов, создание, deep link.
3. **Бот**: анонс при создании, `/polls`, cron итогов.

## Риски / заметки

- Изменение дефолта квоты касается и существующего веб-UI опросов
  (`poll-casting.tsx`): интерфейс должен показывать источник «кошелёк» и
  скрывать квоту, когда `quotaAllowed: false`.
- `future-vision` по-прежнему блокирует опросы — без изменений.
- `pollCost` за создание — без изменений (глобальный кошелёк, burn).
